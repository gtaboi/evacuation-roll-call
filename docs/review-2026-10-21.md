# Code review, 21 Oct 2026

Read-only review in four lenses, plus a local smoke test. Nothing here has been fixed yet. Items marked ★ were checked against the code after the review; the rest are as reported from reading the code. Line numbers refer to commit `3c863f2`.

## 1. Does the code do what README.md and CLAUDE.md promise?

### High
- ★ **"Time to 100%" and "accounted %" count check-in rows, not staff.** `app.js:237`, `app.js:205`, `app.js:757-768`. Visitors not on the staff list and the same person on two phones each count again.
  - Repro: 4 people on the staff list. A and B check in, plus "Visitor 1" and "Visitor 2". The admin sees 100% while C and D are still listed as Missing, and history saves "Met target".
- ★ **Any signed-in user can read every row of `profiles` (old staff emails and names).** `supabase/schema.sql:154` uses `using (true)` for all authenticated users. Public sign-up is probably on (the Supabase default).
  - Repro: `sb.auth.signUp(...)`, confirm the email, then `sb.from('profiles').select('*')`.

### Medium
- ★ **Staff names stay on screen after an admin leaves the admin view.** The Missing list stays visible after Sign out or switching to the Check in tab. `applyView()` skips it (`app.js:294`), and only the admin render hides it (`app.js:590`).
  - Repro: on a shared phone during an event, sign out as admin. Names and "Mark safe" buttons are still shown.
- ★ **"Switch to wet/dry point" can remove the point mid-evacuation.** `app.js:751`. If the other point was never saved, it sets the event's point to null, and every "safe" check-in is then refused.
  - Repro: save only the dry point, start an evacuation, tap "Switch to wet weather point".
- **An admin email with no login yet could be taken over.** `is_admin()` trusts the email in the login token (`schema.sql:77`). Only possible when public sign-up is on and email confirmation is off. Suspected; depends on the Auth settings.

### Low
- An upgraded database keeps the old `profiles` policies and data, so it differs from a fresh `schema.sql` install.

### Confirmed as promised
- Staff only go through the three security-definer functions, and coordinates are never stored.
- Names are matched the same way in the browser and the database, and names can't inject HTML.
- `?v=10` matches in all three places.
- The AI helper checks admin rights.

## 2. Location and time

### High
- ★ **The radius check can be bypassed.** The server only compares the distance the phone sends (`schema.sql:81-91`).
  - Repro: call `rpc('public_checkin', {…, p_status:'safe', p_distance:0})` from anywhere and it's accepted. "I need help" needs no location at all and still counts as accounted for.

### Medium
- **A very inaccurate location still passes.** `app.js:688-695`. Only the centre of the location fix is compared, so a 1.5 km Wi-Fi fix centred on the office passes the 100 m check.
- **Times mix the admin phone's clock with the server's.** End time and "Mark safe" use the phone (`app.js:739`, `:760`, `:779`); start and check-in times come from the server.
  - Repro: an admin phone 3 minutes slow counts "Mark safe" as 0 s after the alarm, and the saved duration is 3 minutes short.
- **Past drills are judged against today's target.** `app.js:506-535`. The target isn't saved with each summary, so changing it rewrites "Met target" for every old drill.

### Low
- `parseCoords` (`app.js:889-899`) misses some formats:
  - whole-number coordinates;
  - degree/N/E formats;
  - Maps links that only give the map's view centre.
- The AI debrief gets the date in UTC (`assist/index.ts:142`), so it can name the wrong day.
- An admin can still mark people safe after the event ends (`app.js:775-781`), but the saved summary is never updated.
- The browser and the database treat a radius of 0 differently.

## 3. Cost, tokens and caching

### High
- **Each admin tab reloads all 9 queries on every change.** `app.js:150-160`, `:195-200`. With about 300 staff checking in, that's roughly 9 requests per second per admin tab, and each one re-downloads all summaries including the debrief text.
- **Staff phones keep polling.** `app.js:1249`. Each phone sends 3 requests every 15 s until the event ends, even after checking in and in background tabs. 500 phones is about 100 requests per second. Each phone also holds a Realtime connection, and the Free plan caps those at 200.
- ★ **A paid debrief can be thrown away silently.** `app.js:828` with `:90`.
  - Repro: click "Write debrief", then "Mark safe" while it's being written.

### Medium
- **Up to 4 paid AI calls per click.** Retries also run on 5xx errors (`assist/index.ts:23-46`).
- **AI results aren't reused.** `match` results are never stored, so every click is billed again.
- **AI output can be fragile.** There's no `response_format`, and the 1500-token cap can cut the JSON short, so the admin clicks again and is billed again.
- **The AI request grows with the staff list.** Full names, help status and distances go to the outside AI provider (`assist/index.ts:96-148`).
- **Every admin action reloads twice** (once directly, once from the Realtime echo).

### Low
- The Google Places session token isn't reset when an admin abandons a search (`app.js:902-914`).

## 4. Loops, timeouts and failure handling

### High
- ★ **A failed check-in says the page "retries automatically", but it doesn't.** The reload's error replaces the check-in error (`app.js:93-94`, `:179`).
  - Repro: start an event, go offline after the location fix, tap "I'm safe".
- ★ **The staff page never recovers if the first load fails.** The poll only runs once an active event has loaded (`app.js:1249`).
  - Repro: block `/rest/v1/events` while loading, then unblock. It stays on "No evacuation in progress".
- ★ **Starting an event isn't atomic.** It deactivates every active event, then inserts a new one (`app.js:739-740`).
  - A stale admin page ends the running event with no summary.
  - Two admins tapping at once can create two active events.
  - If the insert fails, there's no event at all.
- **No request has a timeout.** On a bad connection one stuck request leaves everything disabled with no message.

### Medium
- An overlapping refresh can overwrite a just-made check-in with older data, and "Checked in" disappears for up to 15 s (`app.js:172`).
- A network error during the admin check signs the admin out as "not on the admin list" (`app.js:1219-1225`).
- Empty or cut-off AI output shows a raw "Unexpected end of JSON input" error (`assist/index.ts:50-54`). Upstream calls have no timeout.
- Ending an event is two separate writes, so it can appear in history while still active (`app.js:762-771`).
- Both check-in buttons stay tappable during the up-to-15 s location wait (`app.js:665-707`).
  - Repro: tap "I'm safe" then "I need help". The final status depends on which request lands last.

### Low
- Text typed into "Add person"/"Add admin" is lost if another save is running.
- The "Couldn't load" banner never clears after a later successful load.
- The AI helper reports a database error as "Only admins".
